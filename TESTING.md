# Isolated testing environment

The feature branch is `codex/isolated-testing-environment`. Local testing is a separate Docker Compose project named `veritras-testing`, with its own PostgreSQL volume, Hardhat chain (31337), contract deployment, API, and frontend. It does not read production database or contract values from the root `.env`.

## Run locally

Prerequisites: Docker with Compose v2, Make, and enough free disk for the Node/Python images and build cache. The `vfs` Docker storage driver uses substantially more space than overlay storage.

```sh
make testing-up
make testing-check
make testing-status
```

| Service | URL |
| --- | --- |
| Frontend | http://localhost:13000 |
| API documentation | http://localhost:18000/docs |
| Liveness | http://localhost:18000/health/live |
| Readiness and indexing progress | http://localhost:18000/health/ready |
| Hardhat RPC | http://localhost:18545 |
| PostgreSQL | localhost:55432, database/user `veritras_test` |

All host ports bind to loopback. The fixed database password and JWT key in this Compose file are only for this disposable local stack. The test frontend offers an injected wallet on chain 31337. Configure a local-only browser wallet with the Hardhat RPC above and an account generated by that local chain. Never use a real funded wallet for the unlocked Hardhat accounts.

`deploy-contracts` writes a deployment manifest to a testing-only shared volume. The backend migrates its empty database with Alembic, validates the manifest's chain, and starts indexing from the first deployment block. The frontend receives the same addresses and connects its browser RPC to the published local endpoint. No external API keys or Sepolia funds are needed locally.

`make testing-check` signs in with a test wallet, creates a draft and shipment through the real API, registers the same product, records checkpoints, transfers custody, completes delivery, and checks PostgreSQL-derived API results plus receipt-backed verification. It deliberately refuses a non-Hardhat chain or a non-Compose API hostname. Each run creates a new labeled item; it does not clear the database.

To stop the stack, use `make testing-down`. To discard all testing data and start a new chain/database together:

```sh
make testing-reset
make testing-up
```

Hardhat's chain is ephemeral. After destroying/recreating its container, reset the testing database and cursor volumes together. Restarting only the API preserves its cursor. A cursor ahead of the chain is reported as degraded instead of silently claiming the data is current.

In a managed cloud workspace, Make automatically adds `compose.testing.cloud.yml` when `CODEX_PROXY_CERT` is present. That override mounts the proxy CA only during dependency installation and bind-mounts current source for iteration without repeatedly rebuilding large source layers. It preserves the environment's proxy and registry configuration. `BUILDX_CONFIG` is written under ignored `.testing/`; no global Docker settings are changed.

## Hosted Vercel Preview + Render + Neon

Hosted provisioning requires connected Neon/Render accounts or `NEON_API_KEY` and `RENDER_API_KEY` added through the cloud environment's secret settings. Do not paste keys into chat or commit them. A separate funded Sepolia test signer and RPC are also needed to deploy the hosted test contracts; alternatively, supply an already deployed test-contract manifest.

1. Create a Neon branch for testing. Use its own endpoint in the testing backend's `DATABASE_URL`; do not reuse the production endpoint. Prefer schema-only or sanitized data for public demonstrations.
   If its schema came from a legacy `create_all` deployment, reconcile the Alembic baseline on the test copy before running the initial migration. An existing schema without migration history must not be blindly stamped or migrated as an empty database.
2. Deploy the contracts to separate Sepolia addresses and record their chain ID, deployment blocks, and transaction receipts. Existing production contract addresses are rejected in testing mode. The current deploy script records deployment blocks and accepts `DEPLOYMENT_OUTPUT` for the manifest path.
3. Create a separate Render service using `render.testing.yaml`, pointing to the feature branch. Supply the missing environment values from `backend/.env.testing.example`. Set `INDEXER_START_BLOCK` to the earliest deployment block minus one. Use a separate JWT key. Keep automatic deployment off until the branch's checks pass.
4. Verify `/health/live` reports `environment: testing`, `chain_id: 11155111`, then confirm `/health/ready` reaches `ready`. Platform liveness is deliberately separate from initial catchup and indexing readiness. Monitor readiness for failures; a live process is not proof of current indexing.
5. In Vercel project `veritras`, scope the values in `frontend/.env.testing.example` to **Preview**, initially to this Git branch. Set the exact testing API URL and contract addresses. Browser configuration is public; keep provider administration keys out of `VITE_*` variables.
6. Set the testing backend's CORS origins to the exact intended preview URLs. The generated frontend CSP allows its configured API/RPC origins. The existing production CORS configuration need not be widened for testing.
7. Deploy the feature preview, then check its API target, selected chain, contract addresses, and registration journey. Require successful CI checks before merging to `main`. Changing Preview variables requires a new build.

Preview builds fail closed if `VITE_APP_ENV` is not `testing`, if test contract/API values are missing, or if they match the known live endpoints. CI cannot bypass those preview checks. Production builds also require explicit service and contract configuration. Unit-test builds can use CI defaults but are not deployable testing environments.

## Implemented boundaries and remaining work

This first increment provides isolated local services and hosted configuration, indexer ABI/startup fixes, bounded polling, retry/health reporting, stable bytes32 handling, draft reconciliation, delivery checkpoint deduplication, shipment-status updates, and receipt checks before verification. The login response field now matches the API.

The complete implementation plan remains in `IMPLEMENTATION_PLAN.md`. Object-level API permissions, full SIWE scope/session validation, a transactional database event journal/cursor, reorganization recovery, metadata event handling, and revised analytics remain subsequent increments. Do not treat the local smoke check as coverage of those unimplemented guarantees. The file-based cursor still requires a persistent volume for hosted restarts; Render's free filesystem is ephemeral. Production replay/backfill waits for the durable-indexing increment.

Hosted Neon/Render resources and a usable Vercel preview must be recorded here after successful provisioning. A template alone does not establish a hosted testing environment.

Current hosted access blockers: the managed environment has no Neon/Render credentials. The Vercel connector can inspect `veritras`, but updating its branch-specific Preview variables returned HTTP 403 for team `hoppaysamas-projects`; no variable was changed. Completing hosted setup requires write access to that team or configuring the Preview values manually in the Vercel dashboard. Production settings were not modified.
